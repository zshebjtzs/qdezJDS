# 关键技术决策记录

> 本文档为 AI Agent 提供项目开发过程中的重要决策和原因。
> Agent 在设计新方案时，应参考本文档，避免提出已否决的方案或重复讨论。

## 决策 1：评论嵌套限制为二级

- **日期**：2026-06-14
- **决定**：评论系统采用二级嵌套（评论 → 一级回复 → 二级回复），不实现无限嵌套。
- **原因**：
  1. 社团内部讨论认为无限嵌套会让界面眼花缭乱。
  2. 限制嵌套可以简化前端渲染逻辑（`buildReplyTree` 只处理两层）。
  3. 对话可以通过 `@用户名` 实现定位，不依赖深层嵌套。
- **替代方案**：最初考虑过类似 B 站的无限嵌套，但实现复杂度高且体验不理想。
- **影响**：所有回复最多缩进两级。二级回复下的回复会变成同一一级回复下的新二级回复。

## 决策 2：网盘分页从全量缓存改为后端分页

- **日期**：2026-06-21
- **决定**：网盘文件列表改为后端分页加载（20条/页），弃用全量缓存。
- **原因**：
  1. 全量缓存方式在文件数量增长后性能下降。
  2. 搜索改为后端实现后，分页是必要条件。
  3. 与论坛帖子列表的分页方式保持一致。
- **替代方案**：无，全量缓存已无法满足扩展需求。
- **影响**：修改了 `cloudService.js`、`cloudController.js`、`stores/cloud.js`、前端搜索逻辑。前端 `src/utils/search.js` 已删除。

## 决策 3：热度排序公式

- **日期**：2026-06-14
- **决定**：帖子热度 = `commentCount * 5 + viewCount * 1`。
- **原因**：回复权重大于浏览，鼓励互动。公式简单，性能开销低。
- **替代方案**：曾考虑加入时间衰减因子，但初期阶段不需要复杂算法。
- **影响**：后端 `getPostsByCategory` 的 ORDER BY 使用此公式。以后可调整权重。

## 决策 4：文件搜索使用后端 LIKE 而非前端搜索

- **日期**：2026-06-21
- **决定**：网盘文件搜索由后端执行，使用 MySQL `LOWER() LIKE` 匹配，英文不区分大小写。
- **原因**：
  1. 前端全量缓存已废弃，无法在前端搜索全量数据。
  2. 后端搜索支持高亮匹配位置返回。
- **替代方案**：曾经试图保留前端搜索，但分页导致前端只能搜索当前页数据，体验极差。
- **影响**：后端 `cloudService.js` 新增高亮计算函数 `computeHighlights`，前端 `PrivateCloud.vue` 和 `PublicCloud.vue` 增加高亮渲染。

## 决策 5：验证码集成延后至正式部署

- **日期**：2026-06-21
- **决定**：极验验证码（Geetest）已在登录页和后端预留接口，但暂不启用。
- **原因**：开源仓库会暴露极验 ID，增加风险。等网站正式部署后再启用。
- **影响**：前端 `LoginPage.vue` 和后端 `authController.js` 已集成代码，通过 `git reset` 暂时移除了验证码相关功能，代码保留在本地备份中。

## 决策 6：禁止评论/浏览权限仅管理员和版主可修改

- **日期**：2026-05-01
- **决定**：帖子的 `canReply` 和 `canBrowse` 字段仅管理员或板块版主可修改，帖主本人无权修改。
- **原因**：防止帖主滥用权限（如发布争议内容后锁定评论）。
- **影响**：前端 `postSingle.vue` 中 `canManagePerms` 计算属性不包含帖主本人。

## 决策 7：用户名 3 天冷却修改 (目前前端接口暂未实现)

- **日期**：2026-05-09
- **决定**：用户修改用户名后需等待 3 天（72 小时）才能再次修改。
- **原因**：防止用户名频繁变动导致其他用户混淆。
- **影响**：后端 `changeUsername` 检查 `username_changed_at` 字段，前端显示曾用名。

## 决策 8：管理员紫色、版主红色命名

- **日期**：2026-05-16
- **决定**：管理员用户名显示紫色，版主在管辖板块内显示红色。
- **原因**：用户要求视觉区分权限角色。
- **影响**：全局 CSS 使用 `--color-info` (purple) 和 `--color-moderator` (red)，各组件通过 `usernameClass` 计算属性动态绑定。

## 决策 9：封禁账号与 is_active 分离

- **日期**：2026-05-01
- **决定**：`is_active` 仅用于永久禁用，临时封禁通过 `bans` 表管理。
- **原因**：参考 GitHub、Google 等平台实践，职责分离更清晰。
- **影响**：登录检查先查 `is_active`，再查 `bans` 表。
